# Cross-language byte-for-byte verification

Proves that the `smsg_proto` envelope
(`[name_hash:32][version_hash:32][payload_len:u32le][protobuf payload]`) is produced
**byte-identically** by Rust, Python, Go and Kotlin given the same `.proto` definitions
and the same logical message.

The version/name hashes are computed canonically from the protoc **file descriptor set**,
so any language that hashes the same `.proto` gets the same hashes — no shared runtime,
no FFI, no generated-code consistency problem.

## Files

- `descriptors.pb` — shared descriptor set (generated by protoc from `../proto/*.proto`)
- `golden.json` — baseline output dumped by the Rust `dump_golden` example
- `python/verify.py`, `go/main.go`, `kotlin/Verify.kt` — per-language verifiers
- `kotlin/lib/` — downloaded jars (git-ignored)

## Regenerate the baseline (after schema changes)

```bash
cargo run -p proto_poc --example dump_golden > proto_poc/verification/golden.json
protoc --descriptor_set_out=proto_poc/verification/descriptors.pb \
  --proto_path=proto_poc/proto proto_poc/proto/chat.proto proto_poc/proto/chat_old.proto
```

The Rust crate also has a test (`tests/golden_check.rs`) that fails if the committed
`golden.json` drifts from the current Rust output.

## Run the verifiers

```bash
# Rust (also guards golden.json)
cargo test -p proto_poc

# Python (needs: pip install protobuf blake3)
python proto_poc/verification/python/verify.py

# Go (needs a Go toolchain; deps via go.mod)
cd proto_poc/verification/go && go run .

# Kotlin (needs JDK; jars fetched on demand via script)
bash proto_poc/verification/kotlin/run.sh
```

## Notes

- `name_hash` uses the short message name (stable across schema edits, mirrors soul_msg).
- `version_hash` walks the message fields (name, number, protobuf type, type_name) in
  declaration order — changes when the schema changes.
- Protobuf itself guarantees the payload bytes are identical across implementations;
  the verification confirms it empirically and confirms our canonical hash + envelope
  framing are reproducible in every language.

## Schema-compatibility policy (decode time)

Decoding is policy-driven (`Policy`, default `Strict`):

- **Strict**: the wire name/version hashes must equal the expected message's hashes,
  otherwise `TypeMismatch` / `VersionMismatch` is returned. This is a hard
  "schema identity" guarantee — even a backward-compatible field addition is
  rejected, so endpoints must be upgraded in lockstep.
- **Lenient**: hash verification is skipped; the payload is decoded with protobuf's
  tolerant evolution semantics (extra fields dropped / absent fields defaulted).
  Structural framing (header size, payload length prefix, trailing bytes) is still
  enforced in both modes.
- Note that lenient is *not* "reinterpret any bytes as any type": if the payload's
  wire types cannot be parsed as the target message, the decoder still errors
  (e.g., prost rejects a known field with a mismatched wire type).

Verified in `proto_poc/tests/proto_roundtrip.rs`:
strict rejects version-mismatched (forward and backward) messages while lenient
decodes them with shared fields preserved; framing violations are rejected in both modes.
